# Доменное событие

Скилл — про **смысл события**: что оно утверждает и кто вправе его опубликовать. Устройство
самой шины (очередь, доставка, backpressure) — отдельная тема.

## Событие не опережает состояние

**Событие фиксирует переход, который уже произошёл и уже сохранён.** Это не команда и не
обещание. Опубликован `OrderCanceled` — значит, заказ уже `Canceled` и закоммичен. Подписчик
верит факту и не перепроверяет базу.

### Конструктор стережёт инвариант

`New<Event>` проверяет, что объект в статусе, который означает событие. Это единственная точка
проверки: иначе её пришлось бы повторять в каждом подписчике.

```go
func NewOrderCanceled(order domain.Order) (*OrderCanceled, error) {
	if order.Status() != domain.OrderStatusCanceled {
		return nil, fmt.Errorf("order %s must be Canceled, got %s", order.ID(), order.Status())
	}
	return &OrderCanceled{order: order, occurredAt: time.Now().UTC()}, nil
}
```

Конструктор возвращает ошибку, а не паникует: объект приходит из базы или из запроса, а не из
литерала. Паника допустима только в `Must`-обёртке для тестовых фикстур, где объект собран
литералом и ошибка означает опечатку в тесте. Ошибку конструктора продюсер не глотает и не
«чинит» подстановкой статуса: событие не публикуется, ошибка уходит вверх.

### Продюсер: transition → persist → construct → publish

1. **Перевести** объект в новый статус — новым значением, а не мутацией на месте.
2. **Сохранить** переход.
3. **Собрать** событие — тут и сработает проверка инварианта.
4. **Опубликовать.**

```go
canceled, err := order.Cancel(time.Now().UTC())
if err != nil {
	return fmt.Errorf("cancel order: %w", err)
}
if err := r.orders.Save(ctx, canceled); err != nil {
	return fmt.Errorf("persist canceled order: %w", err)
}
evt, err := events.NewOrderCanceled(*canceled)
if err != nil {
	return fmt.Errorf("build OrderCanceled: %w", err)
}
r.orderCanceled.Publish(*evt)
```

Шаги 2 и 4 местами не меняются. Публикация до коммита покажет подписчику факт, которого в
базе ещё нет: пойдя за деталями, он прочитает старый статус.

### Подписчик реагирует, но переход не записывает

Когда «статус не сохраняется», тянет повесить подписчика, который зовёт `SetCanceled`. **Не
надо**: причина и запись перехода разъедутся по разным местам, и появится окно, где база
отстаёт от уже опубликованного факта. Подписчик — для реакции: уведомить, закрыть сессию,
отправить письмо. Запись перехода — дело продюсера.

## Дырка: dual-write между коммитом и публикацией

Порядок persist → publish убирает одну гонку и открывает другую. Процесс умер между коммитом и
`Publish` (паника, OOM, рестарт при выкладке) — **факт в базе есть, подписчики о нём не узнают
никогда**: ретраить некому. Отказ самого `Publish` при живом процессе — случай легче, его можно
повторить. Итог — не «потерянное сообщение», а молчаливое расхождение: заказ отменён, деньги не
возвращены, соседняя система считает заказ живым.

### Идемпотентных подписчиков хватает, когда шина переживает рестарт

Шина хранит недоставленное и подтверждает обработку (at-least-once) — недоставленное доедет
ретраем, а от дублей спасает идемпотентность. In-process шина так не умеет: для неё остаются
outbox или осознанно принятая потеря. Условия идемпотентности:

- у события **стабильный ключ**: id сущности плюс тип перехода или id записи о переходе — не
  `time.Now()` и не UUID, рождённый заново на каждой попытке;
- обработчик проверяет «уже сделано» или опирается на upsert и уникальный индекс;
- повтор дешевле пропуска.

Так закрываются реакции, которые безопасно повторить: пересчёт кеша, повторное уведомление.
Смерть до `Publish` не закрывает даже брокер: вызова не было, ретраить нечего.

### Transactional outbox

Нужны оба условия:

1. **Одна операция и меняет сущность в базе, и должна уведомить внешний мир.** Outbox делает
   атомарными два действия, которые сами по себе атомарными не бывают. Операция только шлёт
   сообщение и бизнес-таблиц не трогает — шли напрямую: одному действию атомарность не нужна,
   а лишняя таблица — это нагрузка и мониторинг.
2. **Пропуск события дороже инфраструктуры**: списание денег, вызов внешней системы, выпуск
   документа.

Тогда намерение опубликовать коммитится **в той же транзакции**, что и переход:

```go
// в outbox — DTO события, а не доменный объект: у того приватные поля
payload, err := json.Marshal(events.OrderCanceledDTO{OrderID: canceled.ID()})
if err != nil {
	return fmt.Errorf("encode OrderCanceled: %w", err)
}
// одна транзакция: переход и строка outbox коммитятся вместе или не коммитятся вовсе
if err := r.tx.Do(ctx, func(ctx context.Context) error {
	if err := r.orders.Save(ctx, canceled); err != nil {
		return err
	}
	return r.outbox.Add(ctx, outbox.Record{
		Key:     canceled.ID() + ":canceled", // стабильный ключ: повтор постановки — no-op
		Type:    "OrderCanceled",
		Payload: payload,
	})
}); err != nil {
	return fmt.Errorf("cancel order: %w", err)
}
```

Запись outbox обязана взять транзакцию из того же контекста, что и `Save`. Ушла мимо, прямо в
пул, — откат уберёт переход, а строка outbox останется и отправит событие о том, чего не было.
Отдельный воркер (relay) забирает строки и доставляет: смерть в любой точке оставляет строку на
месте, следующий проход её подхватит.

Цена: доставка at-least-once **по построению** — relay мог доставить и умереть до пометки, так
что подписчики всё равно идемпотентны. К задержке добавляется лаг relay.

**In-process шина без outbox — at-most-once на границе процесса.** Это допустимо, если выбрано
осознанно: напиши у продюсера, что теряется при рестарте.

### Порядок событий одной сущности outbox не держит

Порядок вставки строк — не порядок коммитов, а типичный relay берёт строки `FOR UPDATE SKIP
LOCKED`, шлёт пачку параллельно и упавшую строку переносит на потом, пока следующие уходят.
`OrderPaid` может дойти раньше `OrderCreated`.

- Проще всего сделать получателя нечувствительным к порядку: событие говорит «сущность X
  изменилась», обработчик сам перечитывает её текущее состояние и идемпотентен.
- Если порядок нужен на стороне доставки — лок по сущности в relay, а не по строке. Рецепт и
  ловушки (функция лока рядом с `LIMIT`, `REPEATABLE READ`, сессионный лок на пуле) —
  `references/relay-ordering.md`.

## Консьюмер брокера: retry-топик, DLQ или inbox

Для брокера с подтверждением обработки (Kafka и подобные) первый вопрос — **важен ли порядок
событий одной сущности?**

- Не важен (письма, пуши, независимые начисления) — упавшее сообщение в retry-топик с
  отдельной consumer-группой, offset основного топика коммитить сразу; исчерпавшее попытки —
  в DLQ.
- Важен (смена статусов, конечные автоматы) — retry-топик не ставь: позднее сообщение обгонит
  упавшее. Бери inbox или ограниченный ретрай в обработчике с остановкой партиции.
- Бесконечный ретрай в обработчике — никогда: он держит партицию, и всё за упавшим
  сообщением ждёт.

Inbox, дедупликация по `message_id`, DLQ по причине — `references/broker-consumer.md`.

## Тесты

- **Инвариант конструктора** — юнит без базы: неверный статус даёт ошибку, верный — событие.
- **Продюсер** — на реальном Postgres: прогнать продюсера и проверить, что в базе новый статус
  и событие опубликовано (или строка outbox на месте).
- Не публиковать в тесте «голое» событие в обход продюсера: конструктор проверяет статус, так
  что тест сперва переводит и сохраняет объект — повторяет продюсера.
- **Идемпотентность подписчика** — доставить одно событие дважды и убедиться, что эффект
  однократный.
