# resilience — проверка

Файл для того, кто правит скилл: какие утверждения проверены и как их перепроверить.
Claude его не загружает.

## Сверено с документацией

| Утверждение | Раздел | Итог |
|---|---|---|
| `Client.Timeout` нулевой — без тайм-аута; включает соединение, редиректы и чтение тела | `go doc net/http.Client` | ✓ |
| Тайм-аут — по допустимой доле ложных тайм-аутов (0,1%) и соответствующему перцентилю (p99.9) | документация AWS о тайм-аутах, повторах и jitter | ✓ |
| Повторы на каждом уровне перемножаются: 3 попытки на 5 уровнях — 243× | там же | ✓ |
| Клиентские ошибки тем же запросом не повторять | там же | ✓ |
| Объём повторов ограничивают локальным token bucket; breaker вносит режимы, которые трудно тестировать | там же | ✓ |
| Без jitter backoff хуже всех; equal jitter — почти та же работа, что full, но дольше; decorrelated — быстрее full, но больше вызовов | статья AWS с симуляцией видов jitter | ✓ |
| `RETURNING` возвращает только вставленные или обновлённые строки — пропущенные `DO NOTHING` не возвращаются | PostgreSQL 18, INSERT | ✓ |
| В READ COMMITTED `DO UPDATE` срабатывает и по строке, не видимой снимку; `DO NOTHING` может не вставить из-за невидимой транзакции | PostgreSQL 18, Transaction Isolation → Read Committed | ✓ |
| `old`/`new` в `RETURNING`; для `INSERT … ON CONFLICT DO UPDATE` `old` не NULL на конфликте | PostgreSQL 18, INSERT | ✓ |
| `count(*)` из-за MVCC проходит строки; `min`/`max` планировщик превращает в `ORDER BY … LIMIT 1` по индексу | PostgreSQL wiki «Slow Counting»; `planagg.c` | ✓ |
| Значения gobreaker v2 по умолчанию: `ReadyToTrip` — больше 5 отказов подряд, `Interval` ≤ 0 — счётчики closed не сбрасываются, `Timeout` — 60 с, `MaxRequests` 0 — одна проба | комментарий `Settings` и константы в `gobreaker.go` v2.4.0 | ✓ |

## Проверено опытом

2026-11-02, Go 1.27.2, gobreaker v2.4.0, pgx v5.11.0, PostgreSQL 18.6 и 17 (контейнеры).

| Утверждение | Как проверено | Итог |
|---|---|---|
| `http.Client{}.Timeout == 0` | вывод поля | ✓ `0s` |
| `errors.Is(err, context.DeadlineExceeded)` ловит и `Client.Timeout`, и срок контекста | `httptest`-сервер спит 2 с, лимит 200 мс обоими способами | ✓ оба `true`, `net.Error.Timeout()` тоже |
| Отмена родительского ctx обрывает вызов, `WithoutCancel` + свой срок — нет | родитель отменён через 100 мс, срок попытки 500 мс | ✓ без отвязки — 100 мс, `Canceled`; с ней — 500 мс, `DeadlineExceeded` |
| `backoff` не выходит из `[0, min(max, base·2^(n-1)))` и не переполняется | 100 тыс. значений на попытках 1, 3, 64, 1000 | ✓ |
| gobreaker по умолчанию: 5 отказов — closed, 6-й — open; в open функция не вызывается | тест | ✓ `ErrOpenState`, вызова нет |
| `Interval` 0 разбавляет долю: после 1000 успехов порог «≥ 20 вызовов и ≥ 50%» срабатывает на 1000-м отказе | тест | ✓ 1000 |
| Скользящее окно (`Interval` 10 с, `BucketPeriod` 1 с): через 11 с после 1000 успехов хватает 20 отказов | `testing/synctest` | ✓ 20 |
| Half-open: отказ пробы — снова open; 3 успеха при `MaxRequests` 3 — closed; 4-я параллельная проба — `ErrTooManyRequests` | `testing/synctest` | ✓ |
| `IsSuccessful` с отказом адресата не открывает breaker | 10 таких отказов | ✓ closed |
| `min(created_at)` по частичному индексу дёшев при длинной очереди, `count(*)` — нет | 2 млн строк, 400 тыс. `new`, `EXPLAIN ANALYZE` | ✓ `Limit` + `Index Only Scan`, 4 буфера, 0,03 мс; `count` — 1098 буферов, 15 мс |
| После разбора головы до вакуума первый `min` проходит мёртвые записи, следующий — быстрый | 300 тыс. старейших `new` → `sent`, автовакуум выключен | ✓ 300 001 heap fetch, 126 мс; затем 1 fetch, 1,9 мс; после `VACUUM` — 0,04 мс |
| `DO NOTHING RETURNING` на дубле — ноль строк | psql | ✓ |
| CTE + `UNION ALL` при параллельной вставке того же ключа — ноль строк | сеанс A вставил ключ и держит транзакцию, сеанс B ждёт, A коммитит | ✓ 0 строк |
| `DO NOTHING`, затем отдельный `SELECT` в READ COMMITTED находит строку соседа | тот же сценарий | ✓ |
| `DO UPDATE SET key = EXCLUDED.key RETURNING …, old.id IS NOT NULL` возвращает строку и при гонке; дубль — новая версия строки | тот же сценарий; `pg_stat_user_tables` | ✓ `existed = t`; `n_tup_upd` и `n_dead_tup` растут |
| `old` в `RETURNING` — с PostgreSQL 18 | тот же `INSERT` на PostgreSQL 17 | ✓ на 17 — синтаксическая ошибка |
| В REPEATABLE READ параллельная вставка того же ключа с `DO NOTHING` — ошибка сериализации | тот же сценарий | ✓ `could not serialize access due to concurrent update` |
| Пачка под одной арендой: строки ждут свободного воркера, аренда покрывает худший проход × ⌈пачка / N⌉ | опытом не проверялось: следствие того, что аренда ставится на всю пачку при взятии | по построению |
| Фрагменты кода скилла собираются | `go vet` с gobreaker v2.4.0 и pgx v5.11.0 | ✓ |

## Не вошло

- Числа под конкретную нагрузку: тайм-ауты, сроки жизни по классам, порог возраста головы,
  размеры полос. Это замеры и решения продукта; в примерах — иллюстрации.
- Выход из half-open по доле отказов среди проб (так делают не все библиотеки; в gobreaker —
  строго).
- Отсекает ли конкретный провайдер дубли по ключу клиента: зависит от провайдера, общего
  ответа нет.
- Token bucket для синхронных повторов — без кода и чисел.
- Сколько хранить DLQ и шифровать ли payload — решение проекта.
