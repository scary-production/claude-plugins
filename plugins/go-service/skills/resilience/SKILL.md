# Вызовы внешних провайдеров

Скилл — о том, как не дать медленному или лежащему провайдеру и всплеску рассылки положить
остальное. Очередь на `FOR UPDATE SKIP LOCKED` — `go-postgres:postgres-concurrency`,
outbox — `go-service:events`, бюджет остановки — `go-service:architecture`.

## Главное

- У каждой попытки свой тайм-аут; остановка сервиса её не обрывает.
- Отказ классифицируй по тому, мог ли провайдер принять сообщение, а не «повторяемо или нет».
- Повтор — перенос строки очереди с паузой full jitter, пока успевает до конца срока жизни.
- У каждого класса сообщений (коды, транзакционные, рассылки) свои воркеры.
- Приём идемпотентен по ключу продюсера; конфликт ключа — «уже принято», не «доставлено».

Почему: без этого получается один общий пул, клиент без тайм-аута, фиксированная пауза и
повтор любой ошибки. Тогда один больной провайдер или всплеск рассылки останавливает всё.

## Тайм-аут

- **У `http.Client{}` тайм-аута нет** (`Timeout` по умолчанию 0 — без предела). Медленный
  провайдер держит воркера сколько угодно, пул кончается, стоят и здоровые каналы.
- **Срок — на попытку, через контекст запроса**: у разных провайдеров разные сроки, а
  `Client.Timeout` один на клиента. Оба вида тайм-аута ловит
  `errors.Is(err, context.DeadlineExceeded)`.
- **Значение — по гистограмме задержки провайдера**: выбери допустимую долю ложных
  тайм-аутов (0,1% — это p99.9) и добавь запас на сеть. «В 2–3 раза выше p99» — прикидка до
  замеров. Слишком низкий тайм-аут сам рождает повторы и дубли.
- **Остановка сервиса не обрывает вызов.** Оборванный посреди запрос — неизвестный исход и
  возможный дубль. Вызов отвязывается от отмены и ограничен своим сроком; бюджет остановки
  должен покрыть самую долгую попытку.

```go
actx, cancel := context.WithTimeout(context.WithoutCancel(ctx), step.Timeout)
receipt, err := step.Sender.Send(actx, msg)
cancel()
```

## Три исхода отказа

Решает не «можно ли повторить», а «мог ли провайдер принять сообщение»: от этого зависит,
идти ли к запасному.

| Исход | Примеры | Что делать |
|---|---|---|
| Отвергнут навсегда | номера нет, адресат заблокировал бота, адрес не существует | итог `failed`: ни повтор, ни другой провайдер не помогут |
| Точно не принят | отказ в соединении, 5xx до приёма, 429, кончились деньги на счёте | к запасному сразу или повтор позже |
| Исход неизвестен | тайм-аут, обрыв после отправки запроса | провайдер мог принять: к запасному — только если дубль дешевле потери |

- **Неклассифицированная ошибка — «исход неизвестен»**: раз не знаешь, ушло ли, считай, что
  могло.
- **Своя ошибка — сразу итог, без повторов**: неизвестный тип события, битый шаблон,
  payload не разбирается. Повторы битого только жгут воркеров; такое — в DLQ (статус для
  ручного разбора).
- **429 с паузой провайдера**: следующая попытка не раньше неё —
  `next = max(backoff, retryAfter)`.
- **Код отказа машиночитаемый и без персональных данных** (`http_503`, `chat_not_found`): он
  уходит в статус сообщения, журнал попыток и логи.

```go
type FailureKind uint8

const (
	Rejected    FailureKind = iota + 1 // адресат отвергнут навсегда
	NotAccepted                        // провайдер точно не принял
	Ambiguous                          // запрос ушёл, ответа нет
)

type DeliveryError struct {
	Kind       FailureKind
	Code       string        // без адресата и текста
	RetryAfter time.Duration // пауза, которую назвал провайдер
	Err        error
}

func (e *DeliveryError) Error() string { return fmt.Sprintf("%d %s: %v", e.Kind, e.Code, e.Err) }
func (e *DeliveryError) Unwrap() error { return e.Err }

func Classify(err error) *DeliveryError {
	var de *DeliveryError
	if errors.As(err, &de) {
		return de
	}
	if errors.Is(err, context.DeadlineExceeded) {
		return &DeliveryError{Kind: Ambiguous, Code: "timeout", Err: err}
	}
	return &DeliveryError{Kind: Ambiguous, Code: "unclassified", Err: err}
}
```

Адаптер провайдера сам переводит ответы в `DeliveryError`: только он знает, что значат его
коды.

## Повторы

- **Пауза растёт экспоненциально, внутри — full jitter**: случайное значение от 0 до
  `min(max, base·2^(n-1))`. Без jitter пачка, упавшая разом при сбое провайдера, разом и
  повторяется — синхронные пики. Equal jitter (половина паузы фиксирована) делает почти ту же
  работу, что full, но дольше; бери его, только если нужна нижняя граница паузы.

```go
func backoff(attempt int, base, maxD time.Duration) time.Duration {
	d := base
	for i := 1; i < attempt && d < maxD; i++ { // удвоение без переполнения
		d *= 2
	}
	return rand.N(min(d, maxD)) // math/rand/v2; base > 0
}
```

- **Бюджет — срок жизни сообщения, а не число попыток.** У каждого сообщения `expires_at`;
  предел срока — по классу (коды — минуты, транзакционные — часы; числа — решение продукта).
  Не отправляй, если до истечения осталось меньше `minRemaining`: код дойдёт мёртвым. Не
  переноси, если следующая попытка позже `expires_at − minRemaining`: итог `expired`.
- **Повтор — перенос строки очереди, а не `time.Sleep` в воркере**: воркер свободен на время
  паузы, объём повторов ограничен числом воркеров полосы.
- **Повторы — на одном уровне стека.** Если очередь переносит строку, клиент провайдера и
  SDK не повторяют сами (проверь их значения по умолчанию), обработчик не крутит цикл.
  Уровни перемножаются: по 3 попытки на каждом из 5 уровней — 243 запроса.
- **Синхронный вызов в обработчике запроса** без очереди — не больше одного повтора, общий
  объём повторов ограничь локальным token bucket.

## Полосы вместо общего пула

- **Класс сообщения — колонка или топик одной таблицы очереди**, у каждого класса свои
  воркеры, свой backoff и свой предел срока. Две таблицы не нужны.
- **Одного `ORDER BY priority` мало**: коды пройдут первыми, но всплеск рассылки всё равно
  займёт всех воркеров, пока медленный провайдер их держит, а рассылка без своей доли может
  не уйти совсем.
- **Число воркеров = поток × время вызова** (закон Литтла), проверяй при деградации: 12 в
  секунду × 200 мс = 2,4 воркера; провайдер замедлился до 5 с — нужно 60. Худший случай —
  поток × сумма тайм-аутов цепочки провайдеров.
- **Аренда строки длиннее худшего прохода** — суммы тайм-аутов всех провайдеров цепочки плюс
  запас. Иначе аренда истечёт посреди вызова, строку возьмёт второй воркер, и сообщение
  уйдёт дважды. Берёшь пачку под одну аренду, а обрабатываешь по N за раз — строки ждут
  своей очереди под той же арендой: худший проход × ⌈пачка / N⌉.
- **Журнал попыток: запись начала — до вызова провайдера.** Начало без итога в следующем
  раунде — процесс умер посреди вызова: исход неизвестен, возможен дубль. Считай таких в
  метрике.

## Запасной провайдер и circuit breaker

- **Цепочка на пару (канал, класс)**: основной, затем запасные. «Не принят» — к следующему
  сразу; «исход неизвестен» — только там, где дубль дешевле потери (коды подтверждения).
- **Маршрута по умолчанию нет**: нет цепочки для пары — ошибка при приёме, а не тишина и не
  дешёвый провайдер для кодов.
- **Breaker нужен, когда есть куда переключиться.** Без него каждое сообщение сперва ждёт
  тайм-аут лежащего основного. При одном провайдере и очереди он почти ничего не даёт: паузы
  уже разносит backoff.
- **Свой breaker на провайдера**, отказ адресата — успех: провайдер жив. `ErrOpenState` и
  `ErrTooManyRequests` — «не принят»: сразу к запасному.

```go
cb := gobreaker.NewCircuitBreaker[Receipt](gobreaker.Settings{
	Name:         "sms-primary",
	Interval:     time.Minute,      // окно; 0 — счётчики closed не сбрасываются никогда
	BucketPeriod: 10 * time.Second, // скользящее окно вместо фиксированного
	Timeout:      30 * time.Second, // сколько стоять в open до проб
	MaxRequests:  3,                // проб в half-open
	ReadyToTrip: func(c gobreaker.Counts) bool { // минимум вызовов и доля отказов
		return c.Requests >= 20 && c.TotalFailures*2 >= c.Requests
	},
	IsSuccessful: func(err error) bool { return err == nil || Classify(err).Kind == Rejected },
})
```

Значения gobreaker по умолчанию задавай явно, они не про долю отказов:

- `ReadyToTrip` — больше 5 отказов подряд.
- `Interval` 0 — счётчики копятся с последней смены состояния: после 1000 успехов порог 50%
  сработает только после 1000 отказов подряд.
- `Timeout` — 60 с в open; вызов в open не выполняется.
- В half-open любой отказ снова открывает breaker, `MaxRequests` успехов подряд закрывают,
  пробы сверх `MaxRequests` получают `ErrTooManyRequests`.

## Перегрузка: возраст головы очереди

- **Задержку очереди меряй возрастом старейшей записи, а не `count(*)`:**
  ```sql
  CREATE INDEX messages_pending_idx ON messages (created_at) WHERE status = 'new';
  SELECT min(created_at) FROM messages WHERE status = 'new';
  ```
  `min` по такому индексу — `Limit` над `Index Only Scan`, несколько страниц при любой длине
  очереди. `count(*)` проходит каждую ожидающую запись и дорожает вместе с очередью, а
  возраст головы — прямо задержка доставки.
- **Голова очереди после разбора пачки**: до вакуума первый `min` проходит мёртвые записи
  индекса, следующие — уже быстро. Автовакуум таблицы очереди держи частым.
- **Выше порога — явный отказ продюсеру «перегружен»** кодом ошибки по соглашению API, и сверх
  буфера не принимай. Бесконечный буфер — вечный хвост.
- **Молча отбрасывать можно только то, что контракт разрешает терять** (рассылки). Кодам и
  транзакционным — ошибка продюсеру.
- **Брокер перегрузку не лечит**: он переносит очередь в другое место.

## Приём без дублей

- **Ключ идемпотентности — от продюсера** (id его события), уникальный индекс в таблице
  сообщений. Конфликт значит «уже принято»: верни id и текущий статус строки, доставку ведёт
  воркер по статусу. Ответ «обработано» на конфликте теряет сообщение, если первая попытка
  упала до отправки.
- **`ON CONFLICT DO NOTHING RETURNING` на дубле возвращает ноль строк** — в pgx это
  `pgx.ErrNoRows`, не ошибка. Существующую строку читай следующей командой: в READ COMMITTED
  она видит закоммиченную вставку соседа.

```go
err := tx.QueryRow(ctx, `INSERT INTO messages (idem_key, class, payload, expires_at)
	VALUES ($1, $2, $3, $4) ON CONFLICT (idem_key) DO NOTHING RETURNING id, status`,
	key, class, sealed, expiresAt).Scan(&id, &status)
if errors.Is(err, pgx.ErrNoRows) {
	existed = true
	err = tx.QueryRow(ctx, `SELECT id, status FROM messages WHERE idem_key = $1`, key).Scan(&id, &status)
}
```

- **Не сворачивай это в один запрос `WITH ins AS (…) SELECT … UNION ALL SELECT …`**: при
  параллельной вставке того же ключа снимок запроса не видит чужую строку, а вставка уходит в
  `DO NOTHING` — ноль строк, приём не знает, что ответить.
- **Одним запросом — `DO UPDATE`**: `ON CONFLICT (idem_key) DO UPDATE SET idem_key =
  EXCLUDED.idem_key RETURNING id, status, old.id IS NOT NULL AS existed` (`old` в `RETURNING` —
  с PostgreSQL 18). Строка вернётся всегда, но каждый дубль пишет новую версию строки.
- **В REPEATABLE READ** параллельная вставка того же ключа даёт ошибку сериализации — повторяй
  транзакцию целиком.
- **Свой ключ провайдеру** передавай, только если в его документации сказано, что он по
  этому ключу отсекает дубли. Иначе после неизвестного исхода дубль возможен: для кодов
  принимай его (at-least-once), где дубль вреден — не иди к запасному на неизвестном исходе.

## Содержимое в очереди

Телефон, адрес и текст сообщения — персональные данные. Удаляй содержимое вместе с записью
итога, в одной транзакции; в DLQ, журнале попыток и логах — только коды без адресата и
текста. Шифровать ли payload и сколько держать DLQ — решение проекта.
